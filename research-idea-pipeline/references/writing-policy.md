# 受控中文写作政策（落盘文档 / 对话返回 / 子代理意见共用）

本文件管**形式**：句子长度、语态、标点、用词是否一致。
它**不管内容**：证据强度、评分、命名、落盘位置各有专管文件（见 §6）。

**为什么需要它：** 本流水线一天产出几千字（提案、叙事、八份评审意见）。没有人会逐句重读。
读不清的文档等于没写；读不清的评审意见等于白派子代理。受控中文的目标是**消歧**，不是求短。

---

## 0. 三个受管表面

| 表面 | 谁读 | 典型位置 |
|---|---|---|
| **落到文档** | 半年后的你、合作者、下游 agent | `routes/<R>/docs/*.md`（含 **`<R>000-anchor.md` 冻结契约**）、路线 `README.md` / `STATUS.md` / `INDEX.md`、根 `README.md` / `INDEX.md`（含 **锚点变更单** 小节） |
| **返回对话** | 用户 | 每次 Mode 的报告正文 |
| **子代理意见** | Lead（机器间） | 评审意见、交叉质询记录、汇总表 |

> **不在范围内：** 本 Skill 自己的**规范文本**（`SKILL.md`、`references/*.md`）。
> 它们的信息密度优先，**不要**拿 linter 去扫它们。
>
> **在范围内：** `examples/*.md` 与 `templates/*.md` —— 前者是产出样例，后者是产出骨架，
> 都会被照抄进 `docs/`。它们同样按 §2 执行，并纳入 linter 检查。

> **锚点文档与锚点变更单同样受管**，但有一条例外：**它们的 frontmatter 与表头里的
> 枚举值/字段名是机器可读契约，必须原样保留**（见 §8 第 6 条）。
> 规则本身见 [../SKILL.md](../SKILL.md) §0.1 / §0.2 —— 本政策只管这些文档的**句子形式**。

## 1. 三档：asd-ste100 / Strict /「中文-顺」

**asd-ste100 是可选最强档**，另外两档是默认档。

| 档 | 用在 | 执行到哪一步 |
|---|---|---|
| **asd-ste100** | **用户显式声明时**，覆盖本轮**全部**受管表面 | 全部规则。句长上限**不区分指令与说明，一律 ≤ 25 字**；**打开「一词一义」**（含默认关闭的 `synonym-rotation`）；**建议类规则升为硬**（被动语态 / 复合体貌 / 破折号连接 / 半角标点 / 含糊词）；§3 词汇规则从「方向」升为**执行** |
| **Strict** | 程序步骤、命令、路径、报错、判定结论 —— **读错有代价** | 全部规则，含硬性句长上限与「一词一义」 |
| **中文-顺** | 说明性正文：提案、叙事、调研报告、评审意见、对话报告 | **结构规则全部执行**；词汇规则只作方向 |

**怎么选档：**

1. **默认不启用 asd-ste100**，按下面的判定表走。
2. **只有用户能开**（「用 asd-ste100 档」「按 asd-ste100 写」）。声明针对**当次调用**：
   当次产出的**全部**受管表面按 asd-ste100 执行 —— 它**覆盖**判定表，不与判定表逐行合并。
3. **Agent 不得自行升档。** 也不得因「这段读错有代价」就把整轮升成 asd-ste100 ——
   那是用户的开关。
4. 声明**不写进产出、不跨轮继承**。下一轮不说即回到判定表。

**默认判定表（未声明 asd-ste100 时照此执行）：**

| 产出 | 档 |
|---|---|
| R9—R11 实验计划书（14 节步骤）、任何命令与路径 | **Strict** |
| 其余落盘文档正文 | 中文-顺 |
| 返回对话的报告正文 | 中文-顺 |
| 子代理评审意见 | 中文-顺 |

> **`examples/` 与 `templates/` 仍按默认档校验**（`--disable synonym-rotation`）。
> asd-ste100 只约束**当次调用产出**，不追溯改写既有样例。
> 实测：8 个受管文件在默认档下硬违规全为 0；按 asd-ste100 口径会新增 2—20 处，
> 多为**说明性长句**与同义轮换 —— 这正是它只作可选档的原因。
>
> **可照抄的样板：** [../examples/example-writing-tier.md](../examples/example-writing-tier.md)
> 给出同一段内容的两种写法，并逐句标注命中的规则、以及 linter 查不到而必须人工处理的地方。

**为什么说明文不锁死用词：** 全锁死读起来像换了个作者，而不是变清楚了。受控写作修形式，
不修内容；一段空话改完还是空话，只是干净了。

**为什么 asd-ste100 要更严、又不做默认：** 它服务**必须逐字精确**的产出 —— 对外交付、
冻结契约、给外部 agent 的指令。严格档换来的是产能下降，所以开关交给用户；
**默认档才是常规产出（一次几千字）该用的档**。

## 2. 结构规则（硬性，执行）

| 规则 | 这样做 | 不要这样 |
|---|---|---|
| **主动语态** | 脚本删除临时文件。 | 临时文件被脚本删除。（施事未知或无关时才用「被」） |
| **一句一动作** | 打开文件。读第 3 行。 | 打开文件并读第 3 行，然后检查是否匹配。 |
| **句长** | 指令句 ≤ 25 字；说明句 ≤ 40 字 | 一句话套三层从句 |
| **不用分号** | 拆成两句，表格里改用顿号或分行 | 「先做 A；再做 B」，表格单元格里的「…；…」 |
| **名词短语 ≤ 3 层** | 燃油泵阀门 | 高压燃油泵进口阀门总成 |
| **不省略成分** | 未备份的文件会丢失。 | 文件未备份将丢失。（哪些文件？） |
| **保留情态** | 「请求可能已失败」照写 | 把「可能」升级成事实「请求失败」 |
| **段限** | 一段一主题，≤ 6 句 | 一段里塞三件事 |
| **顺序用列表** | ≥ 3 步或 ≥ 3 个条件用编号 / 项目列表 | 把步骤塞进一句 |

> **分号一律不用**（与 linter 的 `semicolon` 规则一致）。中文的「一句」以 `。！？` 计，
> 也以 `；` 计，所以分号把两件事算作了一句。正文里改成 `。`；表格单元格里改成 `、` 或分行。
> 这一条**没有例外** —— 只要 linter 报 `semicolon`，就是硬违规。

## 3. 词汇规则（默认是方向；asd-ste100 档下是执行）

> **档位差别：** 「中文-顺」与「Strict」档下本节只作**方向**；**asd-ste100 档下本节全部作硬性
> 执行**，并额外**打开 `synonym-rotation`**（同义轮换）—— 即默认被关掉的那条规则在本档启用。

| 规则 | 这样做 | 不要这样 |
|---|---|---|
| **一词一义** | 同一动作全篇只用一个动词（一直用「检查」） | 检查 / 校验 / 核对 / 确认 轮着用 |
| **动词优先** | 分析日志。 | 对日志进行分析。 |
| **去营销形容词** | 删掉，或换成可测量的说法 | 无缝、强大、赋能、闭环、极致、一站式 |
| **术语首次定义** | 保留必要术语，首次出现给一句定义 | 直接抛黑话，后面全靠猜 |
| **具体化** | 3 秒内重试 2 次 | 快速重试若干次 |

**虚动词是中文最集中的坏习惯：** `进行 / 作出 / 加以 / 予以 / 给予 / 开展 + 动作名词`
（「进行了实验验证」→「验证了」，「对日志进行分析」→「分析日志」）。它同时做三件坏事：
句子变长、施事被藏起来、动作被抽象成名词。**这一条在任何场合都该改，可以放心硬套。**

**去营销形容词对本流水线尤其重要：** 描述自己产出的方案时，最容易写「无缝衔接」「显著提升」
「强大框架」。这些词不给证据。要么删掉，要么换成测量值（「在 X 上比基线高 2.1 个点」）。

## 4. 中文特有的六种机器味（改写前逐条扫）

每一种都是机械的：能指出具体的词或标点，不需要审美判断。

1. **同义轮换** —— 同一件事在一篇里换了好几个名字（用户 / 客户 / 使用者）。定一个名字，全篇用它。
2. **套话堆叠** —— 需要注意的是、值得一提的是、在一定程度上、某种意义上、不难看出。删掉，或直接说事。
3. **名词化** —— 动作被冻成名词（进行 / 作出 / 加以 / 予以 + 名词）。用动词。
4. **营销形容词** —— 宣称质量而不给证据。删掉，或换成撑得起这句话的测量值。
5. **长句串联** —— 用分号、破折号、「并且 / 同时 / 从而 / 进而」把好几件事串成一句。一句一件事。
6. **翻译腔** —— 「基于……的情况下」「对于……而言」「这是一个……的事实」。说清主语和动作，其余删掉。

## 5. 情态是内容（与 evidence-policy 的接口）

**最重要、也最容易翻车的一条。** 「可能 / 也许 / 有时 / 倾向于 / 初步」承载作者的置信度，
**置信度是内容，不是修饰**。

- 把「实验**可能**受批次效应影响」改成「实验受批次效应影响」，不是简化，是**换了一个结论**。
- 把「结果**初步**支持该假设」改成「结果支持该假设」，同样。

这条是 [evidence-policy.md](evidence-policy.md) 「禁止推断」的**同一纪律的另一种说法**：
那边管「不许升级证据等级」，这边管「不许在改写句子时顺手把情态升成事实」。
**两处冲突时以 evidence-policy.md 为准。**

- **本政策从不要求删情态。** §2 的句长上限最容易引诱人删的正是这些词。宁可超长，不要丢置信度。
- 唯一的例外是复合体貌：当「已经……了」表达**当前相关性**（「任务已完成，结果可以直接读」）
  而不是历史时，保留它；纯粹的历史陈述可以简化。

## 7. 机械校验

```bash
# 本流水线默认口径：关掉 synonym-rotation，其余硬规则 0 容忍
python scripts/ste_lint_zh.py --disable synonym-rotation <文件...>

# 存量文档接入时容忍 N 处硬违规
python scripts/ste_lint_zh.py --disable synonym-rotation --baseline 12 <文件...>

# asd-ste100 档（用户显式声明时）：25 字上限 + 不关任何规则（synonym-rotation 启用）
python scripts/ste_lint_zh.py --max-chars 25 <文件...>
```

**为什么默认关掉 `synonym-rotation`：** 它的中文同义组（`运行 / 执行`、`检查 / 校验 / 核对 / 核查`、
`修改 / 更改 / 变更`、`保存 / 存储`）在本领域**常常是有意区分的术语** —— `执行` Mode 与
`运行` 脚本不是一回事，`变更追踪表` 与 `修改建议` 也不是。硬套会稳定误报。
**术语一致性改由「一份文档内一个概念只用一种写法」的人工要求 + §8 第 3 条覆盖。**

**口径说明：** linter 只做**机械首查**。它不比较原文与改写、不判断情态强度有没有变、
不证明原意被保留。**零违规只说明配置的这几项机械检查没发现问题**，不等于文档可读。

| 规则名 | 严重度 | 查什么 |
|---|---|---|
| `semicolon` | 硬 | 分号把两件事串进一句 |
| `long-sentence` | 硬 | 句长超过上限（默认 40 字） |
| `nominalization` | 硬 | 虚动词 + 动作名词 |
| `marketing-adjective` | 硬 | 营销形容词表命中 |
| `empty-phrase` | 硬 | 套话表命中 |
| `synonym-rotation` | 硬 | **本流水线默认关闭**（见上） |
| `passive-voice` | 建议 | 「被」字句 |
| `compound-aspect` | 建议 | 已经……了 / 正在……中 |
| `vague-word` | 建议 | 若干、一些、相关、适当、必要时 |
| `halfwidth-punct` | 建议 | 中文句中的半角标点 |
| `dash-join` | 建议 | 破折号连接 |

建议类只报告，永不导致失败。`--selftest` 里有「请求可能已失败」必须干净的断言。

> **asd-ste100 档下建议类升为硬，但 linter 不会因此失败**（建议类不改变退出码）。
> 也就是说这条**必须人工执行**：跑完 `--max-chars 25` 之后，逐条确认
> `passive-voice` / `compound-aspect` / `dash-join` / `halfwidth-punct` / `vague-word`
> 的每一处报告都已处置。**不要用退出码 0 冒充 asd-ste100 合规。**

**linter 查不到的两件事（必须人工执行）：**

1. **§8 第 6 条的枚举值一致性** —— linter 不懂 frontmatter 语义。
   机械首查靠 `SKILL.md` §8 A4 的四问（规则 → 字段 → 枚举 → 模板 → 示例五处同步），
   **不是**靠这个脚本。
2. **子代理意见的交叉引用完整性** —— 它只管句子形状，不管"引用的角色/文档 ID 是否存在"。
   那一条归 `roles.md` §5 的输出骨架。

**执行时机：** 落盘**之前**跑一次（SKILL §6 自检清单里有对应项）。返回对话的正文不强制跑 linter，
但 §2 的分号、虚动词、套话三条**必须**遵守。

## 8. 人可读性硬要求（本流水线的增量）

linter 查不到的部分，用下面五条补。

1. **对话返回先给结论。** 第一段就是结论或答案；依据、推导、表格放后面。不要用「首先……其次……」
   铺陈，更不要让用户读到第三段才知道结论。
2. **一段一主题，≥ 3 项就用列表或表格。** 不要把三条并列的发现塞进一个段落。
3. **一份文档内一个概念只用一个写法。** 本流水线的高频术语必须守住：
   `检索等级`（不写「检索层级」）、`新颖性`、`重叠度`、`复现风险`、`方法来源`、
   `评分中位数`、`待核实`、`项目主锚点`、`路线锚点`、`次锚点`、`锚点变更单`。
   措辞强度的用词一律以 [evidence-policy.md](evidence-policy.md) 为准；
   **锚点体系的规则用词以 [../SKILL.md](../SKILL.md) §0.1 / §0.2 为准**。
4. **不用营销形容词描述自己的产出。** 见 §3。
5. **全角标点。** 中文正文里不用半角 `,;:!?`（代码、路径、字段名除外）。
6. **枚举值与字段名不得意译、不得换写法。** 这些是**机器可读契约**，改了就让下游解析失效
   —— 也就是 `SKILL.md` §8 A4 那一类缺陷的产物：

   | 位置 | 只准写 |
   |---|---|
   | frontmatter `core_goal` / `core_goal_secondary` | `theory` / `performance` / `phenomenon` / `benchmark` / `feasibility` / `negative` |
   | frontmatter `anchor_role` | `primary` / `supporting` / `orthogonal` |
   | 锚点变更单 `类型` | `增补` / `替换`（**不写**「新增」「修改」「变更」） |
   | `type` 与文件名 `slug` | §2.1 的**封闭枚举**原样（`anchor` / `field-map` / …） |
   | `subtype` | **自由文本**，按原义写 —— 它是唯一允许自由命名的地方，且**不进文件名** |
   | `epistemic_status` | `Observed` / `Supported` / `Hypothesized` / `Planned` / `Unknown` |
   | 科学分类 `(O, T, R)` | 三轴的**英文枚举原样**（`Method` / `hidden-assumption` / `design-algorithm` …），**各取单值**，不写 `Method+Evaluation` |
   | `anchor_eligibility` | `eligible` / `conditional` / `not-eligible` |
   | 门禁 / 槽位 / 排序维度 | `G1 Claim grounding` … `G5 Venue scope`；`S1 Context` … `S6 Consequence & Boundary`；`Significance` / `Originality` / `Soundness margin` / `Explanatory depth` / `Generality` / `Narrative compression` |
   | 攻击面审稿人名 | `R-Novelty` / `R-Causal` / `R-Experimental` / `R-Theory` / `R-Generalization` / `R-Utility` |

   **反面例子：** 把 `anchor_role: supporting` 写成 `anchor_role: 支撑`，或把 `类型: 替换`
   写成 `类型: 换方向` —— 两者都会让脚本与下一轮 agent 读不出来。
   中文正文里解释时可以写中文（「这条路线是 `supporting`」），**但字段值本身必须原样**。
